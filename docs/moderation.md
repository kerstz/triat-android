# The blocklist ("Don't recommend")

Reference detail moved out of `CLAUDE.md` so it loads only when needed. `CLAUDE.md` keeps the summary, the invariants and the silent-failure index; this file keeps the reasoning and the scars. Markers (`[verified]`, `[scar]`, `[judgement]`, `[drifts]`) mean what `CLAUDE.md` says they mean. If a change contradicts a sentence here, fix the sentence in the same commit.

Subscriptions, the RSS feed, the subscription mix and the import/export of channel lists were removed along with video mode. What follows is the half that outlived them, because a YouTube song is a video keyed by the same id and "stop recommending this" is as meaningful about a song as about a video.

`data/NotInterestedRepository.kt` holds hidden video ids and blocked channels (prefs `not_interested`), process-wide.

**It is the engine of the feature, not a cache in front of YouTube's.** [verified August 2026] Signed out, InnerTube returns no `feedbackToken` anywhere - not on watch-next, browse or search - because there is no account to record against. It is also the only half that acts immediately; YouTube's own feedback is advisory and takes days.

**Signed in, the dismissal is also sent** (`sendDismissalFeedback` → `youtubei/v1/feedback`), so it cleans up recommendations on youtube.com too. `data/NotInterestedActions.kt` is the one place that decides what a dismissal means: the local hide first and synchronously, the account call fire-and-forget on the caller's scope with its result dropped. It must stay that way - the hide has already happened, nothing waits on the network, nothing rolls back on failure. Tokens ride on `VideoItem.dismissal` because they are single-use and bound to the response that carried them; they are null for NewPipe and every signed-out item, so propagation is skipped rather than failed.

[verified August 2026] `/next` and `FEwhat_to_watch` lockups carry both "Not interested" and "Don't recommend channel"; **search carries no tokens at all**. The two entries are told apart by `leadingImage`'s `clientResource.imageName` (`NOT_INTERESTED` versus `REMOVE`), **never by the visible label** - that string is localized and differs per surface. YouTube pre-bakes an `undoFeedbackEndpoint.undoToken` into the same response, carried on `UndoableAction.undoToken`. Success is `feedbackResponses[0].isProcessed`, not the HTTP code; like `subscription/subscribe`, this endpoint answers 200 to requests it did not act on.

**Filtering is a derived flow over the raw fetch**, never a write into it. A tap removes the item next frame with no refetch and Undo restores it in place; mutating the fetched list would make undo a refetch that brings the song back somewhere else or not at all.

**Music shares the store the video feeds wrote to, and shares it deliberately.** A YouTube song *is* a video keyed by the same id, so two sets would let a future surface go on recommending what another was told to drop. `hideSong` writes an ordinary hidden entry; `blockArtist` writes a `BlockedChannel` with a **blank id and the artist's name**, leaning on the name fallback `isFiltered` already has for lockups that omit a channel id - a [Song] carries no artist id, only a name. Matching is whole-string and case-insensitive, never substring, or blocking "Sam" takes "Samantha" with it. The music half is **local only and always will be**: no music feed response Koda parses carries a dismissal token, so there is nothing to propagate - the position every signed-out dismissal is already in. `HomeViewModel.youtubeSongs` filters through it as a derived flow over the raw fetch; **`songs` (the device library) never does**, because "stop recommending this to me" was never a request to hide the user's own files, and the long-press rows are offered only on `SongSource.YOUTUBE`. The player's overflow offers the artist block but not the song hide: the store is a recommendation filter, not a skip list.

Per-surface rules follow the tokens and YouTube's own menus: search offers only the channel block. Undo is a single app-wide `SnackbarHost` at the root of `MainActivity` - the action comes from several surfaces, one of them an overlay above the NavHost, so a per-screen snackbar would be hidden behind the player exactly when needed. That host lives for the whole app, so its `YouTubeRepository` is built lazily (it carries an OkHttp pool and opens EncryptedSharedPreferences). The undo request runs on a `rememberCoroutineScope`, not the snackbar's `LaunchedEffect`, which is cancelled the moment another dismissal replaces it. `ui/moderation/NotInterestedScreen.kt` is the permanent list; without it a mis-tap weeks ago is an invisible, unfixable hole in the feed.
